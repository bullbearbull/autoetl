# ADR-0003: 라이브러리 우선 구조 — 엔진은 순수 패키지, 서버·UI는 얇은 계층

- 상태: 수락됨 (2026-11-04, 계획 확정 사항 기반)
- 결정 주체: 소유자

## 맥락

같은 분석 능력을 Python 라이브러리(확장 3), CLI, 로컬 서버·Web UI, 서버형(확장 9)에서 모두
써야 한다. 서버 API를 유일한 진입점으로 두면 라이브러리 사용자가 프로세스 밖 통신을
감당해야 하고, UI 로직이 엔진에 스며들면 테스트와 재사용이 어려워진다.

## 결정

엔진을 순수 Python 패키지로 두고 나머지는 그 위의 얇은 계층으로 둔다.

- `core`는 결정론 엔진으로 LLM 의존성이 없다. `harness`는 SOP·과업 카드·프로바이더·
  Secure 관문을 담당하고 core 위에서만 돈다.
- SDK(`autoetl as ae`)와 CLI는 SOP 오케스트레이터를 프로세스 안에서 직접 호출한다.
- 로컬 서버(FastAPI)는 엔진 호출을 127.0.0.1 REST/SSE로 노출하는 얇은 계층이다.
- 확장 9(서버형)도 같은 엔진을 재사용하고, 설치 구성(`autoetl[server]`)만 달리한다.

## 대안

- **서버 API가 유일 진입점(라이브러리는 API 클라이언트)**: 배포 일관성은 좋으나 로컬
  프로세스에서도 HTTP 오버헤드와 직렬화 비용을 물어야 한다.
- **화면·서버·엔진을 한 덩어리로 개발 후 나중에 분리**: 분리 시점이 늦어질수록 비용이
  커지고 계층 침범이 굳어진다.

## 결과

- 긍정: 확장 3(라이브러리)과 확장 9(서버형)가 엔진을 그대로 재사용한다. 계층별 단위
  테스트가 쉽고 core의 LLM 무의존성이 구조로 보장된다.
- 부정: 계층 경계 규율이 계속 필요하다(core에서 harness·server import 금지 등). API가
  생기면 계약 관리 비용이 따른다.
