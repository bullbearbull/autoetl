# ADR-0002: 로컬 설치형 우선 — 한 프로세스, Redis·Docker 없음

- 상태: 수락됨 (2026-11-04, 계획 확정 사항 기반)
- 결정 주체: 소유자

## 맥락

1차 사용자는 개인의 로컬 PC에서 쓰는 한 사람이다. 개인 데이터를 다루므로 데이터가
PC 밖으로 나가지 않는 기본 구조가 필요하다. 설치 장벽(Docker 데몬, Redis, 별도 DB)은
도입 실패의 첫 원인이 된다. 다중 사용자·고가용성 요구는 나중의 일이다.

## 결정

개인 로컬 설치형을 먼저 만든다.

- 로컬 서버(FastAPI, 127.0.0.1 전용), 내장 작업 실행기, SQLite 메타데이터를 한 프로세스로
  묶는다.
- Redis나 Docker 없이 `pip install` 한 번(또는 `pipx`·`uv tool install`)으로 실행된다.
- 작업 큐는 프로세스 내 실행기 + SQLite 작업 테이블로 충분히 구현한다.
- 다중 사용자·역할 권한·공유 모델 서버 같은 서버형 요구는 확장 9(별도 설치 구성
  `autoetl[server]`)로 미룬다.

## 대안

- **docker-compose 풀스택(PostgreSQL 메타데이터, Redis 큐)**: 운영형 기능은 빨리 갖춰지나
  로컬 PC 설치 장벽이 커지고 자원 사용이 무거워진다.
- **서버형 먼저**: 팀 시나리오에는 맞지만 1차 사용자(개인)에게 맞지 않고 보안 기본값
  설계(127.0.0.1, Secure Mode)가 늦어진다.
- **데스크톱 앱(Electron 등)**: 배포·업데이트 관리 비용이 크고 웹 기술 스택 재사용이
  어렵다.

## 결과

- 긍정: 설치가 단순하고 자원 사용이 적다. 로컬 전용 바인딩과 Secure Mode로 데이터 보호
  기본값이 자연스럽다. CI도 가볍게 유지된다.
- 부정: 다중 사용자·고가용성·대규모 병렬 작업은 확장 9에서 재설계 비용을 치른다.
  SQLite 메타데이터의 동시성 한계(WAL로 완화)를 고려해 코드가 큐·잠금을 추상화해야 한다.
