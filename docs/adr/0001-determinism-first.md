# ADR-0001: 결정론 우선 — 계산은 코드, LLM은 정해진 결정 지점만

- 상태: 수락됨 (2026-11-04, 계획 확정 사항 기반)
- 결정 주체: 소유자

## 맥락

이 도구의 목표는 어떤 모델을 써도 같은 품질의 스키마 설계가 나오는 것이다. 프런티어 모델
없이 CPU 로컬 모델만 쓰는 PC에서도 완주해야 하고, 벤치마크로 점수를 재서 재현성이 있어야
한다. LLM이 DDL이나 코드를 직접 쓰게 두면 문법 오류, 비결정성, 근거 없는 주장이 생긴다.
반대로 LLM을 아예 쓰지 않으면 모호한 컬럼의 의미 해석과 권고 품질이 떨어진다.

## 결정

측정은 코드가, 판단은 LLM이 맡는다.

- 통계(프로파일), 타입 추론 후보, 관계 분석, 후보 스키마 생성, DDL 컴파일, 검증·채점은
  결정론 엔진(`core`)이 계산한다. LLM 의존성 없이 동작한다.
- LLM은 상태 머신의 정해진 결정 지점(S3 모호 타입, S8 의미 해석, S9 후보 보정, S11 권고,
  S13 적재 플랜 일부)에서만 선택·수정·설명을 한다.
- LLM 출력은 단계별 계약(Pydantic)을 통과해야 다음 단계로 간다. 후보는 코드가 만들고
  LLM은 정해진 목록과 허용 연산(rename, change_type, split, merge, add_index) 안에서만
  고른다(과업 카드).
- 모든 판단에 `evidence` 필드로 프로파일 ID를 인용하게 하고, 검증기가 없는 ID나 통계와
  모순된 주장을 반려한다.
- 재현성을 위해 temperature 0, seed 고정, 프롬프트 해시 캐시를 쓴다.

## 대안

- **LLM이 DDL을 직접 생성**: 프롬프트만으로 빠르게 시작할 수 있으나 모델별 품질 편차가
  그대로 결과에 들어오고, 잘못된 DDL을 코드로 검증하는 비용이 더 크다.
- **완전 규칙 기반(LLM 없음)**: 품질 하한은 가장 높지만 의미 해석·권고 품질이 제한되고
  계획이 요구하는 LLM 하네스 목표(소형 모델로 프런티어의 90%)와 어긋난다.
- **코드와 LLM 역할을 단계별로 뒤섞기**: 지점마다 예외를 두면 흐름 예측이 어려워지고
  벤치 회귀 원인 추적이 어려워진다.

## 결과

- 긍정: 모델 교체의 영향이 계약으로 차단된다. 어떤 모델이든 문법이 틀린 DDL은 나오지
  않는다. 소형 모델 최저 품질이 보장되고 벤치 점수로 변경을 판정할 수 있다.
- 부정: 결정론 엔진을 먼저 다 만들어야 해서 초기 구현 비용이 크다. 과업 카드와 검증기
  설계·유지 비용이 계속 든다. LLM이 쓸모없는 지점까지 호출하지 않도록 조율이 필요하다.
