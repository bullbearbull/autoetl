# Auto ETL 플랫폼 개발 계획

기준일 2026-11-04 · 작성 정민우

> 이 파일은 에이전트가 읽기 위한 계획 사본이다. 원본은 소유자가 관리하는 공유 문서이며, 계획이 바뀌면 소유자가 원본을 고친 뒤 이 파일을 다시 내보낸다. 에이전트는 이 파일을 직접 고치지 않는다.

개인 로컬 설치형 오픈소스로 먼저 만든다. 측정은 코드가, 판단은 LLM이, 검증은 다시 코드가 맡아 어떤 모델에서도 같은 품질을 낸다. MVP는 약 16\~18주이고, 이후 확장 9개를 의존 순서대로 진행한다.

## 확정 사항

다섯 가지 결정으로 대상 DB, 배포 형태, 개발 방식, 공개 범위, 하드웨어 범위가 정해졌다.

| 항목 | 결정 | 설계에 반영된 변화 |
| --- | --- | --- |
| 대상 DB | PostgreSQL | DDL, 타입 매핑, 적재(COPY)를 PostgreSQL 기준으로 먼저 만든다. 다른 DB는 sqlglot 방언 변환으로 나중에 넓힌다 |
| 배포 형태 | 개인 로컬 설치형 먼저 | 로컬 서버, 내장 작업 실행기, SQLite 메타데이터를 한 프로세스로 묶는다. Redis나 Docker 없이 `pip install` 한 번으로 실행된다. 서버형은 확장 9로 따로 설치한다 |
| 개발 방식 | AI 주도, 핵심은 사용자 검토 | 에이전트 프로젝트 게시판과 검토 관문을 둔다. 계약, SOP, 보안 정책, 의존성, 공개 API 변경은 사용자 승인 없이 병합하지 않는다 |
| 공개 범위 | 오픈소스 | Apache-2.0을 권장한다. 핵심 패키지에서 AGPL·GPL 의존성을 빼고, 모델 가중치와 벤치 데이터는 재배포하지 않는다 |
| 하드웨어 | GPU가 없어도, 있어도 동작 | CPU 전용 경로를 기본으로 지원한다. 사양을 점검해 다른 프로그램에 영향이 적은 모델을 추천하고 자원 사용량을 제한한다 |

## 핵심 설계 원칙

가장 중요한 원칙은 LLM이 DDL이나 코드를 직접 쓰지 않는 것이다. LLM은 JSON 스키마 모델을 허용된 연산으로만 고치고, DDL과 적재 코드는 sqlglot·SQLAlchemy가 만든다. 그래서 어떤 모델을 써도 문법이 틀린 DDL은 나오지 않는다.

| 원칙 | 내용 | 효과 |
| --- | --- | --- |
| 결정론 우선 | 통계, 타입, 관계, 후보 스키마, DDL은 코드가 계산한다. LLM은 정해진 지점에서 선택·수정·설명만 한다 | 작은 모델에서도 최저 품질 보장 |
| 계약 우선 | 단계별 입출력을 Pydantic 스키마로 고정한다. LLM 출력도 계약을 통과해야 다음 단계로 간다 | 출력 정형화, 모델 교체의 영향 차단 |
| 로컬·라이브러리 우선 | 엔진은 순수 Python 패키지로 두고, 로컬 서버와 UI는 그 위의 얗은 계층으로 둔다 | 확장 3이 거의 공짜, 서버형도 같은 엔진 재사용 |
| 보안 기본값 | 민감도 분류가 LLM 라우팅, 외부 전송, 로그 기록을 결정한다 | Secure Mode와 확장 7·8의 토대 |
| 평가 주도 | P0부터 정답이 있는 벤치마크로 모든 변경을 점수로 판단한다 | 최소·권장 모델의 근거 |
| 어댑터 구조 | 입력 소스, 탐지기, 스키마 전략, 대상 DB, LLM, 도메인 사전, 추론 백엔드를 플러그인으로 둔다 | 어떤 업무 현장에도 적용 |
| 넓은 호환성 | Windows·macOS·Linux, x86\_64·arm64, Python 3.10 이상을 지원한다. 선택 기능은 쓸 때만 import한다 | 설치 실패와 리소스 낭비 최소화 |

## 로드맵

MVP 7단계 뒤, 로컬 서빙(2)이 OCR(4)과 API 설계자(7)를 연다. 화살표는 선행 → 후행이다.

```text
[MVP · 약 16~18주]
P0 기반 설계(2주) → P1 분석 엔진(4주) → P2 하네스·Secure Mode(4주) → P4 적재 실행(3주) → P5 벤치마크(3주) → P6 릴리스 v0.1(2주)
P1 → P3 로컬 UI(4주, P2와 병행) → P4

[확장 · 요구 번호]
MVP v0.1 → 3. Python 라이브러리(2주)
MVP v0.1 → 2. 로컬 모델 서빙, Unsloth 우선(3~4주)
MVP v0.1 → 1. API 수집·문서 괴리 분석(4주)
MVP v0.1 → 5. 프로젝트 매니저(4주)
2 → 7. 보안 설계 포함 REST API 설계자(4주)
2 → 4. VLM OCR(6~8주)
1, 5 → 6. 수집 감시(3주)
5, 6 → 9. 서버형 확장(4주)
8. 보안 목적 로그 최소화: P0부터 모든 단계에 내장하고 마지막에 고도화
```

OCR(4)은 로컬 서빙(2)만 끝나면 시작할 수 있어서, 업무상 급하면 순서를 앞당길 수 있다.

## 시스템 아키텍처

외부 LLM으로 가는 길은 Secure 관문 하나뿐이다. SDK는 엔진을 직접 부르고, 웹 화면은 로컬 서버를 거친다.

```text
Web UI (React SPA) → 로컬 서버 (FastAPI, 127.0.0.1 전용, SSE, 작업 실행기) → SOP 오케스트레이터
Python SDK·CLI → SOP 오케스트레이터 (프로세스 안에서 직접 호출)

SOP 오케스트레이터 (상태 머신, 흐름 제어는 코드)
├─ 결정론 엔진(core): 수집·프로파일·타입 추론·관계 분석 / 품질 진단·민감도 분류 /
│                     후보 스키마 생성·DDL 컴파일 / 시험 적재·적재 실행·보고서 (LLM 없이도 동작)
│   ├→ 메타데이터 SQLite (작업·실행 이력)
│   └→ 대상 PostgreSQL (DDL·COPY)
└─ LLM 하네스: 단계 브리프·과업 카드·체급별 설정 / 출력 강제·검증 루프·대체 경로
    ├→ 로컬 LLM (Unsloth·llama.cpp·vLLM·Ollama) : 원문 허용(신뢰 구역)
    └→ Secure 관문 (페이로드 생성기 → 전송 차단 장치) → 외부 LLM (OpenAI·Anthropic 호환) : 메타데이터만
사양 점검·추천기 (CPU·RAM·GPU 여유 측정) → 로컬 LLM : 모델 추천·자원 제한
```

SDK는 같은 엔진을 프로세스 안에서 직접 부르므로, 라이브러리(확장 3)와 서버형(확장 9)이 엔진을 그대로 재사용한다.

## 기술 스택과 저장소 구조

로컬 설치형이므로 외부 서비스 없이 한 프로세스에서 돌아가는 구성을 고른다. 서버형에서만 필요한 구성은 확장 9로 미룬다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 런타임 | Python 3.10 이상, uv | 넓은 호환성 |
| 분석 | pandas, numpy, scipy, scikit-learn, statsmodels. 대용량은 DuckDB + pyarrow | 요구 라이브러리 + 전수 데이터의 메모리 문제 대응 |
| 파일 입력 | charset-normalizer, python-calamine/openpyxl, pyarrow, lxml | CP949·EUC-KR 인코딩, 한국식 엑셀 양식 |
| SQL | SQLAlchemy 2.x, psycopg 3, sqlglot | PostgreSQL 적재, DDL 생성·파싱 검증 |
| 시험 적재 | 사용자 PostgreSQL의 임시 스키마. PostgreSQL이 없으면 pip로 설치되는 내장 PostgreSQL 배포판을 검토 | PostgreSQL이 없는 PC에서도 DDL 검증 |
| 계약 | Pydantic v2 | JSON Schema로 내보내 출력 강제에도 사용 |
| LLM 연동 | 자체 경량 어댑터 (openai·anthropic 공식 SDK의 base\_url 재지정) | 구조화 출력과 effort를 프로바이더별로 제어 |
| 로컬 서버 | FastAPI + Uvicorn (127.0.0.1 전용), SSE | 확장 7·9와 같은 스택 |
| 작업 실행 | 프로세스 내 작업 실행기 + SQLite 작업 테이블. Redis 큐는 서버형에서만 | 로컬에 별도 설치 불필요 |
| 메타데이터 | SQLite (WAL) + Alembic | 설치 없이 동작 |
| 프론트엔드 | React + TypeScript + Vite SPA, ECharts, React Flow(ERD), Monaco(DDL) | 빌드 결과물을 휠에 넣어 `autoetl ui` 한 줄로 실행 |
| 사양 점검 | psutil, 선택적으로 NVML(NVIDIA)·Apple Silicon 정보 | GPU 유무와 관계없이 동작 |
| 리포트 | Jinja2 → HTML/PDF/Markdown | 출력 정형화 |
| 로깅 | structlog + 민감정보 가림 처리기 | 확장 8 |

```text
autoetl/
├─ src/autoetl/
│  ├─ contracts/    단계별 입출력 계약 (버전 관리)
│  ├─ core/         결정론 엔진, LLM 의존성 없음
│  ├─ harness/      SOP · 과업 카드 · 프로바이더 · 출력 강제 · Secure 관문
│  ├─ hardware/     사양 점검 · 모델 카탈로그 · 추천기 · 자원 제한
│  ├─ adapters/     입력 소스 · 대상 DB · 탐지기 · 도메인 팩
│  ├─ report/  server/  sdk.py  cli.py
├─ web/             React SPA
├─ bench/           벤치 데이터 생성기 · 실행기 · 리더보드
├─ tools/board/     에이전트 프로젝트 게시판
├─ docs/            설계 결정 기록(ADR) · SOP 문서 · 모델 가이드
└─ AGENTS.md        에이전트 작업 규칙
```

## 표준 분석 절차(SOP)

분석은 15단계(S0\~S14)로 고정하고, 단계마다 담당과 산출물 계약을 정해 둔다. LLM이 맡는 단계는 4개뿐이다.

| # | 단계 | 담당 | 핵심 기법 | 산출물 |
| --- | --- | --- | --- | --- |
| S0 | 수집·정규화 | 코드 | 인코딩 감지, 구분자·헤더 추론, 다중 행 헤더와 병합 셀 해제, 모든 값을 문자열로 로드 | `IngestManifest` |
| S1 | 샘플링 전략 | 코드 | 전수/샘플 판정, 층화·시간 균등 샘플, 전수 통계는 DuckDB로 스트리밍 | `SamplingPlan` |
| S2 | 구조 프로파일 | 코드 | 결측률, 고유값 수, 카디널리티 비율, 길이 분포, 형태 마스크(`9999-99-99`), 중복 행 | `ColumnProfile[]` |
| S3 | 타입 추론 | 코드 + LLM(모호할 때만) | 물리·의미 타입 2계층, 탐지기 신뢰도 점수, 임계치 미달 컬럼만 LLM에 질의 | `TypeAssignment[]` |
| S4 | 타입별 심화 통계 | 코드 | 수치: 분포, 왜도, 이상치(IQR, IsolationForest), 정밀도. 범주: 엔트로피. 시계열: 빈도, 결측 구간, 계절성(STL·ACF) | `ColumnStats[]` |
| S5 | 관계 분석 | 코드 | 후보 키, 근사 함수 종속(FD), 포함 종속(FK 후보), Pearson·Spearman·Cramér's V·상관비·상호정보량, 파생 컬럼, 계층 구조 | `RelationGraph` |
| S6 | 품질 진단 | 코드 | 완전성·유효성·일관성·유일성, 형식 혼재, 심각도별 이슈 목록 | `QualityReport` |
| S7 | 민감도 분류 | 코드 (+로컬 모델) | 주민번호, 카드번호(Luhn), 전화, 이메일, 계좌, 주소 탐지와 체크섬 검증, L0\~L3 등급 | `SensitivityMap` |
| S8 | 의미 해석 | LLM | 컬럼 의미, 엔터티 식별, 표준 영문 이름, 업무 도메인 추정 | `SemanticModel` |
| S9 | 후보 스키마 생성 | 코드 생성, LLM 보정 | 3NF 정규형, 스타 스키마, 단일 와이드, 시계열 최적화(파티셔닝·BRIN), 하이브리드(JSONB) | `SchemaCandidate[]` |
| S10 | 검증·채점 | 코드 | DDL 파싱, 임시 스키마 시험 적재, 제약 위반·데이터 손실률, 평가 기준표 점수 | `Scorecard[]` |
| S11 | 권고 | LLM | 비교, 장단점, 추천 사유 (근거 ID 인용 필수) | `Recommendation` |
| S12 | 선택 | 사용자 | 후보 선택과 수정, 수정 후 재검증 | `SelectedSchema` |
| S13 | 적재 플랜 | 코드 + LLM | 매핑, 변환 규칙, 적재 순서, 증분 전략, 오류 행 격리 | `LoadPlan` |
| S14 | 보고서 | 코드 | JSON을 템플릿으로 렌더링 | `Report` |

### 타입 체계

- 물리 타입: integer, decimal(p,s), float, boolean, string, date, time, timestamp(tz), json, binary
- 의미 타입: 식별자(대리 키·자연 키), 코드값, 명목·순서 범주, 연속·이산 수치, 카운트, 금액, 비율, 일시, 기간, 위경도, 주소, 자유 텍스트, 이메일, 전화번호, URL, 주민등록번호, 사업자등록번호, 우편번호, 법정동코드, 불리언 유사값(Y/N, 예/아니오, O/X), 중첩 JSON
- 규칙으로 처리하는 함정: 앞자리 0 코드, 엑셀 날짜 시리얼, `yyyyMMdd` 정수 날짜, 천 단위 콤마와 통화 기호, 결측 표기(`-`, `N/A`, `해당없음`), 다중 행 헤더

### 후보 스키마 평가 기준표

항목별로 0\~100점을 매기고, 업로드 때 고른 용도(운영 OLTP, 분석·리포팅, 보관·감사)에 따라 가중합한다. 같은 데이터라도 용도가 다르면 정답 스키마가 달라지기 때문이다.

- 무결성: 제약 범위, FD 보존, 무손실 조인
- 중복도, 용도 적합성, 적재 단순성, 저장 효율, 확장 용이성
- 보안 격리: 민감 컬럼을 별도 테이블로 분리했는지

## LLM 하네스

하네스의 목표는 소형 모델 점수를 프런티어 모델의 90% 이상으로 끌어올리는 것이다. 흐름은 코드가 제어하고, LLM은 상태 머신의 정해진 결정 지점에서만 호출한다.

### SOP를 따르게 하는 장치

- SOP를 코드로 관리한다. `sop/v1.yaml`에 단계, 목표, 입출력 계약, 점검 항목, 실패 시 행동을 적고, 사람용 문서와 프롬프트를 같은 원본에서 만든다.
- 단계 브리프를 매 호출에 같은 형식으로 넣는다. 현재 위치, 이전 결정 요약, 이번 과업, 출력 스키마, 점검 항목이 들어간다.
- 모든 판단에 `evidence` 필드로 프로파일 ID를 인용하게 한다. 없는 ID나 통계와 모순된 주장은 검증기가 반려한다.
- 확신도가 낮으면 사용자 질문을 만든다. 예: "`cd` 컬럼은 코드값인가요?" 비대화 모드에서는 기본값을 쓴다.

### 과업 카드

후보는 코드가 만들고 LLM은 정해진 목록과 허용 연산 안에서만 고른다. 소형 모델의 성능 저하를 막는 핵심이다.

| 카드 | 입력 | 출력 |
| --- | --- | --- |
| `T-TYPE-RESOLVE` | 모호한 컬럼 1개의 프로파일 | 의미 타입 목록 중 하나 + 근거 |
| `T-NAME` | 원본 컬럼명과 의미, 도메인 사전 후보 | 표준 영문 이름 |
| `T-ENTITY-GROUP` | FD 기반 엔터티 묶음 후보 | 묶음 선택 또는 수정 |
| `T-CANDIDATE-REVIEW` | 후보 스키마 + 점수표 | 허용 연산만 사용: rename, change\_type, split, merge, add\_index |
| `T-RECOMMEND` | 점수표 | 순위와 사유 |

### 체급별 설정

| 항목 | S (소형·로컬) | M (중형) | L (프런티어) |
| --- | --- | --- | --- |
| 과업 단위 | 컬럼 1개 또는 결정 1개 | 테이블 단위 | 데이터셋 전체 |
| 출력 강제 | 문법 제약 디코딩(JSON schema, GBNF) | JSON schema | JSON schema + 도구 호출 |
| 예시(few-shot) | 3개 | 1\~2개 | 0\~1개 |
| 반복 응답 다수결 | 3\~5회 | 선택적 2\~3회 | 1회 + 자기 검토 |
| 컨텍스트 | 압축 프로파일(상위 k개), 4k\~8k | 표준 | 전체 + 추가 통계 요청 도구 |

체급은 능력 탐지와 벤치 결과로 자동 지정하고 사용자가 바꿀 수 있다. 세 체급의 출력 계약은 같다.

### 출력 강제와 검증 루프

1. 네이티브 구조화 출력(json\_schema strict 또는 도구 호출 강제)을 쓴다.
2. 지원하지 않으면 프롬프트로 JSON을 요청하고 파서로 복구한다.
3. 그래도 실패하면 검증 오류를 포함해 다시 요청한다.
4. 최종 실패 시 코드가 정한 기본값을 쓰고 "LLM 미확정"으로 표시한다.

검증기는 참조 컬럼 존재, 타입과 통계의 일치(소수점이 있는데 INTEGER 금지), 실제 데이터에서 PK 유일성, FK 포함률 임계치, 예약어 충돌을 확인한다. 재현성을 위해 temperature 0, seed 고정, 프롬프트 해시 캐시를 쓰고, 버전 정보만 기록한다.

### 프로바이더 어댑터와 역할

- 프로토콜은 OpenAI 호환(Chat Completions, 필요하면 Responses)과 Anthropic 호환(Messages) 두 가지다.
- 설정 항목: 프로토콜, Base URL, Key, 모델명, Effort, 최대 토큰, 타임아웃, 동시성, 신뢰 구역(로컬·사내) 여부
- Effort는 OpenAI 계열에서 `reasoning_effort`, Anthropic 계열에서 thinking 예산이나 effort 파라미터로 바꾼다. 모델이 지원하지 않으면 무시하고 경고한다.
- 연결 테스트 때 구조화 출력, 도구 호출, 컨텍스트 길이, effort 반영 여부를 실제 호출로 확인한다.
- 역할별 라우팅: 결정 담당, 로컬 파서(Secure 모드 원문 처리), 평가 담당(벤치 채점)에 각각 다른 모델을 지정할 수 있다.

## Secure Mode

Secure 모드에서 외부 LLM으로 나가는 실제 셀 값은 0건이다. 원문이 꼭 필요한 판단은 로컬 모델이 처리하고, 추상화한 설명만 내보낸다.

| 모드 | 외부 LLM에 전달되는 것 | 원문 처리 |
| --- | --- | --- |
| Off | 통계 + 마스킹된 샘플 행 (민감 컬럼은 자동 마스킹) | 외부 LLM |
| Secure | 통계·형태·분포 같은 메타데이터만 | 로컬 모델이 요약한 추상 설명만 전달 |
| Strict | 없음 | 전 과정 로컬 모델 |

### 전달 범위

- 전달하는 것: 컬럼명(옵션으로 `col_07` 같은 별칭), 타입 후보, 결측률, 고유값 수, 형태 마스크 분포(`9999-99-99` 87%), 길이 분포, 반올림·구간화한 수치 통계, 토큰으로 바꾼 범주(`CAT_01` 32%), FD·포함률·상관계수, 품질 이슈 유형
- 전달하지 않는 것: 실제 셀 값, 실제 범주 레이블(허용 목록 예외), 개별 값이 드러나는 최솟값·최댓값, 자유 텍스트 발췌

### 전송 차단 장치

1. 외부로 나가는 페이로드는 계약 스키마 기반 생성기로만 만든다.
2. 전송 직전에 원본 고유값의 해시 집합(Bloom filter)과 개인정보 정규식으로 검사한다. 일치하면 차단하고 알린다.
3. 전송 내역 확인 화면에서 무엇이 나가는지 사용자가 직접 본다.
4. 감사 기록에는 해시, 크기, 수신처만 남긴다.

### 로컬 파서 경로

자유 텍스트처럼 메타데이터만으로 판단할 수 없는 컬럼은 로컬 모델이 원문을 읽는다. 그 결과로 "한국어 상품 리뷰, 평균 2문장" 같은 추상 설명을 만들고, 이 설명도 차단 장치를 통과해야 나간다. MVP에서는 로컬 엔드포인트를 신뢰 구역 프로바이더로 등록하면 동작하고, 서빙 관리는 확장 2에서 만든다.

## 사양 점검과 리소스 친화 모델 선정

사양을 측정하고, 자원 정책으로 쓸 수 있는 예산을 정한 뒤, 예산 안에 들어가면서 벤치 품질 기준을 넘는 모델을 추천한다. GPU가 없는 PC가 기본 경로이고, GPU는 있으면 쓰는 가속 수단이다.

### 추천 절차

1. 사양 점검: OS, CPU 코어 수와 명령어 집합(AVX2, AVX-512, NEON), 전체·여유 RAM, GPU 종류(NVIDIA, AMD, Apple Silicon, Intel)와 전체·여유 VRAM, 디스크 여유, 배터리 사용 여부, 다른 프로그램의 현재 CPU·메모리 사용량
2. 자원 예산 계산: 아래 정책의 상한과 "현재 여유 − 안전 여유분" 중 작은 값
3. 메모리 추정: 가중치 파일 크기 + KV 캐시 + 런타임 여유분. KV 캐시는 과업 카드가 실제로 쓰는 컨텍스트(S 체급 4k\~8k)로 계산해 과다 할당을 막는다
4. 속도 추정: CPU는 메모리 대역폭을 활성 파라미터 크기로 나눠 대략 계산하고, 로드 후 짧은 실측(토큰/초)으로 보정한다. MoE 모델은 활성 파라미터 기준이다
5. 후보 선정: 모델 카탈로그에서 예산에 맞는 것 → 최소 품질 기준 통과 → 품질·속도·자원 점수로 정렬 → 1순위와 대안 2개를 이유와 함께 제시
6. 맞는 모델이 없을 때: 더 잘게 나눈 S 체급 과업, 규칙 기반 모드, 또는 외부 API(Secure 모드) 중에서 고르도록 안내

### 자원 정책 (초기 제안값)

| 정책 | RAM 상한 | CPU 스레드 | GPU | 쓰는 상황 |
| --- | --- | --- | --- | --- |
| 가벼움 (기본) | 여유 RAM의 30% | 물리 코어의 절반 | 여유 VRAM의 50%, 또는 사용 안 함 | 다른 작업과 병행 |
| 균형 | 여유 RAM의 50% | 물리 코어 − 2 | 여유 VRAM의 80% | 일반 사용 |
| 최대 | 여유 RAM의 80% | 전체 | 전체 | 분석만 하는 시간 |

추천 예시: 여유 RAM 9GB에 가벼움 정책이면 예산은 약 2.7GB다. 이때 3\~4B급 4비트 양자화 모델을 1순위로 제시하고, 예상 메모리와 예상 속도를 함께 보여준다.

### 모델 카탈로그

저장소에 버전 관리되는 JSON으로 둔다. 항목은 모델·양자화별 파일 크기, 전체·활성 파라미터, 지원 백엔드, 라이선스, 한국어 처리 수준, 구조화 출력 지원, 과업 카드별 벤치 점수, 하드웨어 프로필별 실측 속도다. 새 모델이 나오면 벤치를 돌려 항목을 추가한다.

### 백엔드 선택

| 하드웨어 | 1순위 | 대안 |
| --- | --- | --- |
| GPU 없음 | Unsloth 또는 llama.cpp 서버의 CPU 실행(GGUF) | Ollama |
| NVIDIA | Unsloth 또는 llama.cpp(CUDA, 부분 오프로드) | vLLM (VRAM이 넉넉할 때) |
| Apple Silicon | Unsloth 또는 llama.cpp(Metal) | MLX 계열 |
| AMD·Intel GPU | llama.cpp(Vulkan 또는 ROCm) | CPU 실행 |

### 실행 중 보호 장치

- 스레드 수 제한, 프로세스 우선순위 낮춤(Unix nice, Windows BELOW\_NORMAL)
- 컨텍스트 상한, 유휴 시 자동 언로드(예: 5분)
- 여유 VRAM에 맞춘 GPU 오프로드 층 수 자동 계산
- 메모리 압박을 감지하면 작업을 잠시 멈추고 사용자에게 알림

MVP(P5)에서는 사양 점검과 추천 안내까지만 하고, 자동 다운로드·기동·자원 제한은 확장 2에서 만든다.

## 벤치마크와 최소·권장 모델 선정

최소 모델은 필수 관문을 통과하고 최고 모델 점수의 85% 이상인 모델 중 가장 작은 것이다. 권장 모델은 95% 이상 중 비용·자원 대비 효율이 가장 좋은 것이다. 두 기준 모두 초기 제안값이고, 변경은 사용자 검토 대상이다.

### 정답이 있는 데이터셋

- 역정규화 후 복원: 스키마 정답을 아는 공개 관계형 DB(Chinook, Northwind, Sakila, TPC-H 등)를 조인해 평면 CSV·엑셀로 만들고, 원래 구조를 얼마나 복원하는지 측정한다
- 잡음 주입으로 난이도를 나눈다: 결측, 형식 혼재, CP949 인코딩, 다중 헤더, 앞자리 0
- 한국형 실데이터는 사람이 정답 스키마를 붙인다
- 체크섬까지 유효한 합성 개인정보로 민감도 탐지와 유출을 시험한다
- 오픈소스 라이선스를 위해 원본 데이터는 저장소에 넣지 않고, 생성 스크립트로 만든다
- 규모: v0 20세트 → v1 50세트 이상

### 지표

| 영역 | 지표 |
| --- | --- |
| 타입 | 물리·의미 타입 정확도 (컬럼 단위 F1) |
| 관계 | PK·FK 정밀도와 재현율, FD 복원율 |
| 구조 복원 | 컬럼-테이블 배정 일치도(ARI), 테이블 수 오차 |
| DDL·적재 | 파싱 성공률, 시험 적재 성공률, 데이터 손실률 |
| 안정성 | 같은 입력 N회 실행 시 스키마 차이, JSON 준수율, 재시도 횟수 |
| 보안 | Secure 모드 유출 0건 (카나리 값 검사) |
| 비용·자원 | 토큰, 지연, 비용, 최대 메모리, CPU 점유율 |

### 실험 조합과 판정

- 조합: 모델(체급별 2\~4개) × effort × Secure 켜기/끄기 × 하네스 켜기/끄기 × 3\~5회 반복
- 하드웨어 프로필: CPU 전용 노트북(RAM 8GB·16GB), Apple Silicon, NVIDIA GPU에서 실측해 카탈로그의 속도·메모리 값을 채운다
- 하네스를 끈 조건은 같은 모델에 단일 프롬프트를 주는 것이다. 이 비교로 하네스가 모델 간 격차를 얼마나 줄이는지 보여준다
- 필수 관문: DDL 성공 100%, 유출 0건, JSON 준수율 99% 이상
- 하네스 목표: S 체급 점수가 L 체급의 90% 이상
- 프롬프트나 SOP를 바꿀 때 CI에서 회귀 시험을 돌리고, 점수가 떨어지면 병합을 막는다

## MVP 단계별 이행 계획

MVP는 7단계, 약 16\~18주다. AI 주도로 구현 속도는 빨라질 수 있지만, 실제 일정을 정하는 것은 사용자 검토 관문이다. 세부 과업과 진행 상태는 에이전트 게시판에서 관리한다.

### P0. 기반 설계 (2주)

- MVP 범위(포함/제외) 확정, 설계 결정 기록(ADR) 작성
- 계약 v0: `IngestManifest`부터 `Report`까지 Pydantic 모델과 JSON Schema 내보내기
- SOP v0 문서와 YAML 초안, 데이터·로그 등급 정책 v0
- 벤치 데이터셋 생성기와 정답 형식 v0
- 저장소, CI(ruff, mypy, pytest, 라이선스 검사), 오픈소스 기본 파일, AGENTS.md, 에이전트 게시판
- 완료 기준: 계약 검토 완료, 빈 파이프라인이 벤치 v0 위에서 도는 것

### P1. 결정론 분석 엔진 (4주)

- S0\~S7, S9(규칙 기반 후보), S10(검증), S14 보고서 초안
- 탐지기 플러그인 구조와 한국형 도메인 팩(주민번호, 사업자번호, 법정동코드, 전화번호)
- 대용량 대응: 청크 처리와 DuckDB, FD 탐색의 조합 폭발 제어(좌변 2\~3개 제한, 샘플 탐색 후 전수 검증)
- PostgreSQL DDL 생성기와 타입 매핑(통계 기반 decimal 정밀도, varchar 길이, timestamptz)
- 완료 기준: LLM 없이 벤치 v0에서 유효 DDL 100%, 기준 점수 기록, `autoetl analyze x.csv --no-llm` 동작

### P2. LLM 하네스와 Secure Mode (4주)

- 프로바이더 어댑터 2종, 능력 탐지, effort 변환
- 오케스트레이터, 단계 브리프, 과업 카드(S3·S8·S9·S11·S13)
- 출력 강제 4단계, 검증기, 대체 경로, 캐시
- 페이로드 생성기, 전송 차단 장치, 로컬 파서 역할, 로그 가림 처리 기본 적용
- 완료 기준: 벤치 점수가 기준선보다 상승, 카나리 유출 0건, 프런티어 1개와 CPU 로컬 모델 1개로 전 과정 완주

### P3. 로컬 서버와 Web UI (4주, P2와 병행)

### P4. 적재 플랜과 실행 (3주)

- 매핑 명세: 원본 → 대상, 변환식, 형 변환, 결측 처리, 중복 제거, upsert 키
- FK 의존 순서대로 적재, 증분 방식(append, upsert, 기준 시각 컬럼)
- 시험 적재(임시 스키마) → 위반 리포트 → PostgreSQL COPY 적재, 실패 행은 격리 테이블로
- 내보내기: `ddl.sql`, `load_plan.yaml`, 단독 실행 ETL 스크립트
- 완료 기준: 정상 행 기준 적재 성공률 99% 이상, 다시 실행해도 결과가 같음

### P5. 벤치마크·모델 선정·사양 추천 (3주, 이후 상시)

- 모델 카탈로그 v1과 사양 점검·추천 안내 v1
- 완료 기준: 최소·권장 모델을 문서와 설정 화면에 명시, RAM 8GB CPU 전용 PC에서도 추천 모델로 완주

### P6. 안정화와 릴리스 (2주)

### 3. Python 라이브러리

```python
import autoetl as ae

ae.configure(provider="anthropic", model="<모델명>", api_key="...", secure=True)
result = ae.analyze("sales/*.csv", purpose="analytics")
plan = result.choose()          # 인자를 생략하면 추천안
plan.ddl(); plan.load("postgresql://...")
```

- 입력: 경로, 글롭, DataFrame, 폴더. 설정 우선순위는 코드 > 환경변수(`AUTOETL_*`) > `~/.autoetl/config.toml`
- LLM을 설정하지 않으면 규칙 기반 모드로 동작하고 안내한다
- 선택 설치 묶음: `[ui]`, `[local]`, `[ocr]`, `[server]`
- 완료 기준: 새 가상환경에서 설치 후 코드 5줄 이내로 분석과 DDL 생성

### 2. 로컬 모델 서빙 (Unsloth 우선)

- Unsloth(Studio/Desktop)는 한 포트에서 OpenAI 호환(`/v1/chat/completions`, `/v1/responses`)과 Anthropic 호환(`/v1/messages`) API를 제공하고, 내부에서 llama-server로 GGUF를 서빙한다 ([Unsloth API 문서](https://unsloth.ai/docs/basics/api))
- 1단계 연결: Unsloth 엔드포인트·키 등록, `/v1/models`로 로드 모델 확인. llama-server, vLLM, Ollama, LM Studio도 같은 방식
- 2단계 관리: `unsloth run` 프로세스 시작·중지·상태 점검, 사양 추천과 연결된 자동 다운로드, 자원 정책에 맞는 기동 옵션(스레드, 컨텍스트, GPU 층, effort)
- 보안 기본값: 127.0.0.1 바인딩, `--disable-tools`로 서버 측 도구(코드 실행·웹 검색) 차단, 외부 터널(`--secure`) 경유 엔드포인트는 Strict 모드에서 불허
- 3단계(선택): 과업 카드 단위 학습 데이터로 Unsloth에서 소형 모델을 LoRA 미세조정하고 GGUF로 내보내 벤치로 비교
- 완료 기준: CPU 전용 PC에서도 로컬 모델만으로 Strict 모드 완주

### 1. API 데이터 수집·문서 괴리 분석

- 입력: Base URL, 인증 방식, 문서(OpenAPI 명세 또는 PDF·DOCX·HWP·HTML 활용 가이드)
- 문서 계약 추출: OpenAPI는 직접 파싱, 비정형 문서는 LLM이 추출하고 사람이 표로 확인
- 빠짐없는 검수 계획: 엔드포인트 × 필수 파라미터 × 대표값, 페이지네이션 끝까지, 오류 코드 유도. 기본은 GET만 허용하고 변경성 메서드는 명시 승인
- 괴리 리포트: 문서에만 있는 필드, 응답에만 있는 필드, 타입·형식·필수 여부·코드값·총건수 불일치를 심각도별로
- 이후 S2\~S14를 그대로 적용하고 증분 수집 코드를 생성

### 5. 프로젝트 데이터 매니저

- 프로젝트 단위: 소스, 스키마 버전, 적재 이력, 결정 기록, 대화, 용어집
- 멀티턴 맥락: 대화 원문 대신 프로젝트 상태 요약과 관련 산출물 검색으로 구성해 소형 모델도 처리
- 새 데이터 추가 시 스키마 진화안, 마이그레이션 DDL, 호환성 판정(기존 구조를 깨는지)
- 데이터 계보, 데이터 카탈로그, 수집→분석→설계→적재→감시 보드

### 6. 데이터 수집 감시

- 주기: 시간 단위 또는 매 수집 직후
- 로컬 설치형은 앱이 꺼져 있어도 돌도록 가벼운 백그라운드 프로세스(`autoetl daemon`)나 OS 스케줄러(Windows 작업 스케줄러, launchd, systemd timer)에 등록한다
- 점검: 가용성, 인증 만료, 스키마 변화, 건수 이상, 최신성 지연, 자동 생성 품질 규칙, 분포 변화(PSI, KS), 적재 실패
- 알림: OS 알림, 이메일, 웹훅. 본문에 민감 값을 넣지 않는다

### 7. 보안 설계 포함 REST API 설계자

- 생성물: FastAPI(기본) 또는 Flask 프로젝트, 모델·DTO·필터·페이지네이션, OpenAPI 문서, Uvicorn 설정, 테스트
- 민감도 맵 기반 보안 설계: 인증, 역할·행·열 단위 권한, 민감 필드 마스킹, 속도 제한, 감사 로그, OWASP API Top 10 대응표, STRIDE 위협 모델
- 민감 테이블이 포함된 설계 작업은 로컬 모델로 자동 라우팅
- 완료 기준: 퍼징·권한 우회 테스트 통과, 민감 필드 노출 0건

### 4. VLM OCR 문서화와 적재

- 전 과정 로컬(Strict 강제). 외부 맞춤법 검사기도 쓰지 않는다
- 흐름: 전처리 → 레이아웃 분석 → 로컬 VLM 인식 + 보조 OCR 엔진 교차 검증 → 문서 구조 복원 → 내보내기
- 출력: 표·장부는 XLSX, 공문·보고서는 HWPX/HWP([python-hwpx](https://github.com/airmang/python-hwpx), Apache-2.0, 품질 검증 필요), 일반 문서는 DOCX
- 오류 탐지 신호: 문자 신뢰도, 두 엔진 불일치, 형태소 분석 비단어, 로컬 LLM 맥락 불일치, 규칙 검증(날짜, 표 합계, 체크섬), 혼동 글자 쌍
- 위험 점수로 자동 승인 / 검토 권장 / 검토 필수를 나눠 따로 제공하고, 정정 내용은 사용자 사전과 미세조정 데이터로 쌓는다
- CPU 전용 PC도 고려해 소형 OCR 모델 + 배치 처리(야간·유휴 시간)를 기본 경로로 둔다

### 9. 서버형 확장 설치

- `pip install autoetl[server]`로 같은 엔진 위에 설치하는 별도 구성
- 다중 사용자와 역할 권한, SSO(OIDC), PostgreSQL 메타데이터, Redis 작업 큐, Docker Compose 배포, 공유 모델 서버
- 로컬 프로젝트를 서버로 옮기는 내보내기·가져오기

### 8. 보안 목적 로그 최소화

- 등급: L0 운영, L1 내부(컬럼명·통계), L2 기밀(샘플 값·데이터 포함 프롬프트), L3 제한(개인정보·비밀 키)
- L3는 절대 기록하지 않고, L2는 디버그를 직접 켠 때만 암호화해 보존 기한 후 자동 삭제
- 이벤트 타입을 고정한 구조화 로그, 예외 추적 정보의 지역 변수 수집 차단, 외부 라이브러리 텔레메트리 차단
- 프로젝트별 암호화 키를 삭제해 일괄 파기하고, 감사 로그는 누가·언제·어떤 객체·무엇을 했는지만 남긴다
- 카나리 테스트: 고유 문자열을 심은 데이터로 전체 파이프라인을 돌린 뒤 로그·DB·임시 파일·캐시를 검색하고, 한 건이라도 나오면 CI 실패
- 로컬 서빙 도구의 기록 정책도 점검한다. 예: Unsloth API 모니터에 프롬프트·응답이 표시되는데, 저장 여부는 확인이 필요하다

## AI 주도 개발 운영

에이전트가 구현하고, 사용자는 검토 관문에서만 승인한다. 진행 보고와 검토 요청은 이 PC에서 도는 에이전트 프로젝트 게시판으로 모은다. 계획 변경은 이 문서에서, 실행 상태는 게시판에서 관리한다.

### 작업 흐름

1. 사용자가 단계 목표를 승인한다.
2. 에이전트가 과업을 쪼개 게시판에 올린다. 과업 하나는 브랜치(또는 git worktree) 하나다.
3. 에이전트가 과업을 맡고(claim) 진행 보고를 남긴다.
4. 테스트, 린트, 타입 검사, 벤치 회귀, 카나리 검사를 통과시킨다.
5. 검토 필요 과업은 검토 요청을 올리고 멈춘다. 나머지는 CI 통과 후 완료한다.
6. 사용자가 게시판에서 승인하거나 수정 요청을 남긴다.

### 검토 관문

**반드시 사용자가 검토하는 변경**

- 계약(contracts), SOP, 과업 카드의 판단 기준
- Secure Mode, 외부 전송, 로그 정책
- 새 의존성 (라이선스 확인)
- 벤치 판정 기준과 최소·권장 모델
- 공개 API(SDK·CLI) 시그니처, 보안 코드(키 저장, 인증), 릴리스

**에이전트가 진행하는 변경 (CI 통과 조건)**

- 계약을 바꾸지 않는 내부 구현과 버그 수정
- 테스트 추가, 동작을 바꾸지 않는 리팩터링, 문서 보완

### 에이전트 프로젝트 게시판

- 저장소의 `tools/board/`에 두고, Python 표준 라이브러리만 써서 추가 설치 없이 동작한다.
- 저장: SQLite 파일 하나(`.board/board.db`). 같은 저장소의 git worktree들이 게시판 하나를 공유한다. git에는 올리지 않고, 필요하면 Markdown 스냅샷을 내보낸다.
- 에이전트용: CLI, 선택적으로 MCP 서버(Claude Code 등에서 도구로 사용).
- 사람용: 127.0.0.1에서 열리는 로컬 웹 화면. 상태별 칸반, 검토 대기 목록, 과업별 보고 타임라인, 승인·수정 요청, 에이전트 활동 상태를 보여준다.
- 규칙: 검토 필요 과업은 에이전트가 직접 완료할 수 없고, 승인은 사용자만 한다. 한 과업은 한 에이전트만 맡는다. 오래 갱신이 없는 과업은 정체로 표시한다.

### 에이전트 코딩 절차 (AGENTS.md)

1. 코드와 데이터를 먼저 읽고 이해한다.
2. 요청과 현재 코드를 비교해 수정 대상을 찾고, 전체를 검토한 뒤 계획을 세운다.
3. 계획대로 차례로 수정한다.
4. 요청 충족 여부와 기존 동작 훼손 여부를 다시 검사한다.
5. 실제 데이터로 실행하고 결과물을 확인한다. 문제가 없어질 때까지 수정·실행·검사를 반복한다.
6. 요청 밖의 로직은 바꾸지 않는다.

## 오픈소스 운영

라이선스는 Apache-2.0을 권장한다. 특허 조항이 있어 기업이 도입하기 쉽고, 주요 의존성과 충돌하지 않는다.

- 의존성 정책: 핵심 패키지는 MIT, BSD, Apache-2.0, PSF, MPL-2.0 같은 허용형만 쓴다. AGPL·GPL 라이브러리(예: PyMuPDF, Ultralytics)는 핵심에서 빼고, CI에서 라이선스를 자동 검사한다.
- 모델: 가중치는 재배포하지 않고 사용자가 받는다. 모델마다 라이선스가 달라 카탈로그에 표기한다.
- 데이터: 벤치 원본은 넣지 않고 생성 스크립트만 둔다. 공공데이터는 이용 조건(공공누리 유형)을 확인한 뒤 쓴다.
- 텔레메트리는 기본으로 없다.
- 저장소 파일: LICENSE, README(한·영), CONTRIBUTING, CODE\_OF\_CONDUCT, SECURITY.md(취약점 비공개 신고), 이슈·PR 템플릿, CHANGELOG, AGENTS.md
- 릴리스: PyPI Trusted Publishing, SBOM, 서명된 태그
- 외부 기여자의 PR도 같은 검토 관문과 CI를 거친다.
