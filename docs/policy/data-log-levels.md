# 데이터·로그 등급 정책 v0

기준일 2026-11-05 · 근거: docs/PLAN.md(확장 8 보안 목적 로그 최소화, Secure Mode 절) ·
기계 판독형 정의: `src/autoetl/security/levels.py`

이 정책의 변경은 소유자 검토 대상이다(AGENTS.md 3절). 실제 강제 장치(로그 가림
처리기, 전송 차단 장치, 카나리 실행기)는 P2 이후 이 문서를 따라 구현한다.

## 1. 두 가지 등급 체계

데이터 등급과 로그 등급은 별개다. 데이터 등급은 데이터 자체의 민감도를, 로그 등급은
기록되는 정보의 민감도를 매긴다.

### 1.1 데이터 등급(민감도, S7 SensitivityMap)

컬럼 단위로 매겨지고 코드 탐지기(주민번호·카드번호 체크섬 등)가 판정한다.
정의체는 `autoetl.contracts.SensitivityLevel`.

| 등급 | 이름 | 예시 |
| --- | --- | --- |
| L0 | 운영 | 일반 업무 데이터(주문 수량, 상태 코드) |
| L1 | 내부 | 식별자, 내부 코드, 통계로 쓸 수 있는 개인정보 아님 값 |
| L2 | 기밀 | 전화번호, 이메일, 주소, 이름, 계좌 |
| L3 | 제한 | 주민등록번호, 카드번호, 비밀 키, API 키 |

### 1.2 로그 등급(기록되는 정보의 민감도)

로그·저장 매체에 담기는 정보 단위로 매긴다. 정의체는
`autoetl.security.levels.LogLevel`. 요약은 `LOG_LEVEL_POLICY` 표.

| 등급 | 이름 | 담을 수 있는 것 | 기록 | 보존 |
| --- | --- | --- | --- | --- |
| L0 | 운영 | 작업 상태, 단계 진행, 오류 코드, 성능 지표 | 항상 가능(평문) | 30일 |
| L1 | 내부 | 컬럼명, 통계, 형태 마스크 분포, 품질 이슈 유형 | 항상 가능 | 30일 |
| L2 | 기밀 | 샘플 값, 데이터가 포함된 프롬프트·응답 | 사용자가 디버그를 직접 켰을 때만, 암호화해서 | 24시간 후 자동 삭제 |
| L3 | 제한 | 개인정보 원문, 비밀 키 | **절대 기록하지 않는다** | — (기록 금지) |

L3 대신 감사 기록에는 존재 사실·종류·해시만 남긴다. 프로젝트별 암호화 키를
삭제하면 L2 기록을 일괄 파기할 수 있어야 한다.

## 2. 등급별 규칙

### 2.1 기록

- 모든 로그는 이벤트 타입을 고정한 구조화 로그(structlog)로 남긴다. 자유 형식
  문자열 로그를 새로 만들지 않는다.
- 예외 추적 정보에서 지역 변수 수집을 차단한다(traceback 포맷터 설정).
- 감사 로그는 누가·언제·어떤 객체·무엇을 했는지만 남긴다. 데이터 값은 들어가지
  않는다.
- 외부 라이브러리의 텔레메트리·사용 통계는 기본 차단한다.

### 2.2 전송(외부 LLM)

모드별 허용 범위는 `TRANSMISSION_RULES` 표와 같다.

| 모드 | 샘플 행 | 메타데이터 | 실제 셀 값 | 비고 |
| --- | --- | --- | --- | --- |
| Off | 마스킹 후 허용 | 허용 | 금지 | 민감 컬럼 자동 마스킹. 사용자 수용 전제 |
| Secure | 금지 | 허용 | 금지 | 컬럼명 옵션 별칭, 범주 토큰, min/max 구간화. 원문 판단은 로컬 모델의 추상 설명으로 대체 |
| Strict | 금지 | 금지 | 금지 | 외부 전송 0건. 전 과정 로컬 |

추가 원칙:

- Secure 모드 페이로드는 계약 스키마 기반 생성기가 만든 것만 나간다.
- 전송 직전 Bloom filter·개인정보 정규식으로 검사해 일치하면 차단하고 알린다.
- 감사 기록에는 해시·크기·수신처만 남긴다.
- 벤치마크 보안 지표: **Secure 모드에서 카나리 유출 0건**이 필수 관문이다.

### 2.3 보존·파기

| 등급 | 보존 | 삭제 |
| --- | --- | --- |
| 로그 L0·L1 | 30일(설정 가능) | 만료 후 자동 삭제 |
| 로그 L2 | 24시간(디버그 활성화 시에만 존재) | 만료 후 자동 삭제, 암호화 저장 |
| 로그 L3 | 없음 | 기록 자체를 시도하면 안 됨(시도는 경고로 남김) |
| 임시 파일·캐시 | 작업 생존 기간 | 작업 종료 시 삭제(평문 잔존 금지) |

프로젝트 단위 파기: 프로젝트별 암호화 키를 삭제하면 해당 프로젝트의 L2 기록을
읽을 수 없게 만든다(일괄 파기).

## 3. 금지 패턴

코드 리뷰와 카나리 테스트가 찾는 대상. `FORBIDDEN_PATTERNS`와 같은 목록.

1. 셀 값을 f-string·포맷·문자열 연결로 로그·예외 메시지에 끼워 넣기
2. traceback에 지역 변수(행·데이터프레임·프롬프트 원문) 노출 — locals 수집 금지
3. 개발용 print·디버그 출력을 커밋
4. 감사 로그·DB 메타데이터에 실제 값 저장 — 해시·집계값만
5. Secure 모드 페이로드에 개별 값이 드러나는 min/max, 실제 범주 라벨, 자유 텍스트 발췌 포함
6. 예외 원문(예: `e.strerror`)을 상위 로그로 그대로 전파
7. 외부 라이브러리 텔레메트리·사용 통계 전송 활성화
8. 작업 종료 후 임시 파일·캐시에 원본 데이터 평문 잔존

## 4. 카나리 테스트 설계

"기록·전송 경로 어디에도 실제 값이 남지 않는다"를 실험으로 증명하는 절차.

1. **심기**: 벤치 생성기가 합성 데이터의 컬럼마다 `CANARY-<uuid4>` 표식 값을
   심는다. 표식 값은 실행마다 새로 만든다(고정값 금지 — 로그 필터 우회 방지).
2. **실행**: 카나리 데이터로 전 과정(S0~S14)을 Secure 모드와 Strict 모드로 각각
   실행한다. LLM 호출이 있는 구성에서는 외부 전송 페이로드 기록(감사)도 포함.
3. **검사 대상**: (a) 로그 파일·콘솔 캡처 (b) SQLite 메타데이터 (c) 임시 디렉터리·
   캐시 (d) 감사 기록의 외부 전송 페이로드 (e) 결과물(ddl.sql, load_plan.yaml,
   보고서).
4. **판정**: 카나리 문자열이 데이터 '값'으로 1건이라도 발견되면 CI 실패. 예외
   허용: 형태 마스크 같은 추상 표현, 카나리 존재 사실을 말하는 감사 문구(값 아님),
   격리 테이블·오류 리포트처럼 사용자가 원본을 봐야 하는 결과물의 해당 컬럼.
   허용 범위는 검사기가 화이트리스트로 관리한다.
5. **CI 통합**: 파이프라인이 실제로 돌게 되는 P1 완료 직후 벤치 v0에 카나리
   데이터셋을 추가하고, P2(Secure 관문) 완료 시 CI에 카나리 잡을 올린다. 이후
   프롬프트·SOP 변경 때마다 회귀 시험으로 함께 돌린다.
6. **확장**: 로컬 서빙 도구(예: Unsloth API 모니터)의 기록 정책도 점검 대상에
   넣는다(외부 기록에 카나리가 남는지).

## 5. 구현 규칙 (P2·확장 8에서 강제)

- `structlog` 프로세서 체인에 등급 판정·가림 처리기를 둔다. 이벤트 타입은 상수로
  고정하고 새 이벤트는 등급을 명시해서 등록한다.
- 전송 차단 장치(페이로드 생성기 → 검사 → 차단)는 `TRANSMISSION_RULES`를 코드로
  읽어 판정한다. 규칙 표와 코드가 어긋나면 테스트가 실패한다.
- 모든 임시 파일은 작업 컨텍스트에서 생성·종료 시 삭제한다.
- 이 문서와 `levels.py`는 함께 고친다(정합성 테스트가 둘을 대조한다).
